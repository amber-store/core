# Reference store on SQLite

**Date:** 2026-09-23
**Status:** directed by the user on 2026-09-23: "use sqlite for the ref store",
"open it with WAL so it supports concurrent writers", "changing refs should
offer optimistic updates (changing ref from key1 -> key2 only if the ref was
key1)", "use sqlc and add support for schema migrations (future proofing)".
Stage 1 of 3 on the way to a jj backend. Implemented on branch
`refstore-sqlite`.
**Repos:** `amber-store/core` (this change); `amber-store/core-rs` follows by
adopting the file format and the migration files defined here.

## Background

`refstore` keeps reference records (name → CBOR record bytes) in a Pebble DB
at `<store>/refs/`. Four properties of that choice block a process-per-command
client such as jj, and the CLI itself:

- **Single process.** Pebble locks its directory at every open, read-only
  opens included. Two commands cannot overlap, not even two readers.
- **Slow to open.** Measured on the development Mac with 1000 references, one
  open per call: Pebble needs 31.6 ms to open, read one reference and close,
  and 43.9 ms to open, put and close. SQLite needs 0.4 ms and, with full
  syncs, about 15 ms.
- **Two formats.** The Rust port uses redb, so a `refs/` directory written by
  one implementation cannot be opened by the other. A tool that opens a store
  it cannot read sees no references at all, and a GC run from it would treat
  every object as garbage.
- **Blind writes only.** A put overwrites unconditionally, so two writers of
  one name lose an update silently. A branch or bookmark push cannot detect
  that the reference moved.

## Goal

The `refstore` API on a SQLite database in WAL mode: any number of processes
may hold the store open, readers never block, writers queue. Reference
writes gain an optimistic form, conditional on the key the reference
currently points at. Queries are generated by sqlc from SQL files, the
schema is built by numbered migrations so it can evolve, and the file format
is specified so that every implementation shares it. Existing Pebble stores
migrate on first open, and binaries that predate this change fail loudly on a
migrated store instead of seeing an empty one.

## Non-goals

- Cross-process safety of a reference put racing a GC sweep. The packstore's
  exclusive directory lock still serializes whole processes; that protocol
  belongs to stage 2, which removes the lock.
- Conditional forms of `ingest --ref` and `commit create --ref`.
- Removing the Pebble dependency. It stays, used only by the migration, until
  a later release drops migration support.
- The `core-rs` port.

## The file format

`<dir>/refs.sqlite`, a SQLite 3 database. This section and the files in
`refstore/migrations/` are the contract other implementations follow.

| Property | Value |
| --- | --- |
| `PRAGMA application_id` | `0x616D6272` (`"ambr"`, 1634558578) |
| `PRAGMA user_version` | the number of migrations applied; `1` today |
| Journal mode | WAL, mandatory |
| Schema at version 1 | `CREATE TABLE refs (name BLOB NOT NULL PRIMARY KEY, record BLOB NOT NULL) WITHOUT ROWID` |

`name` holds the reference name's bytes and `record` the canonical CBOR record
verbatim. Both are BLOBs, never TEXT or NULL: an empty name or record is a
zero-length BLOB. BLOB keys compare with `memcmp`, so `ORDER BY name` is the
bytewise lexicographic order the API promises. The record stays the single
source of truth: no column duplicates a field of it.

## Schema migrations

`refstore/migrations/NNNN_description.sql`, numbered contiguously from `0001`,
embedded in the binary. A file holds plain SQL, one or more statements, and
never changes once released; a schema change is a new file.

At open, inside one `BEGIN IMMEDIATE` transaction:

1. Read `application_id`, `user_version` and the number of schema objects.
2. No id, version 0 and no objects: the database is fresh; set the
   application id. The id differs, or it is absent on a non-empty database:
   refuse the file, it is not a reference store.
3. `user_version` greater than the newest embedded migration: refuse the
   file, a newer release wrote it.
4. Apply every migration numbered above `user_version`, in order, then set
   `user_version` to the newest number and commit.

One transaction means a crash leaves the old version intact, and two
processes opening a store at once agree on the result: the second waits for
the write lock and finds nothing left to do. `user_version` is the only
bookkeeping, so there is no migrations table for other implementations to
mirror; the Rust port can run the same SQL files with the same rule.

A process that opened the store before another process migrated it keeps
running its old queries, so migrations must stay compatible with the release
before them (add, do not rename or drop) or be rolled out with no old process
running.

## Generated queries

`refstore/queries.sql` holds every statement, annotated for sqlc;
`refstore/sqlc.yaml` points sqlc's SQLite engine at the migrations directory
as the schema. `go generate ./refstore` (sqlc comes from the Nix dev shell)
writes `refstore/internal/refsdb`, which is committed, so building needs no
sqlc. CI runs `sqlc diff` so the committed code cannot drift from the SQL;
the generated headers omit the sqlc version to keep that check stable across
patch releases.

## Concurrency

WAL mode is what makes the store multi-process: readers work from a snapshot
and never block, and one write transaction runs at a time. A second writer,
in this process or another, waits for the first up to a busy timeout (30 s)
and then fails with SQLite's busy error. Inside one process a mutex
serializes writers first, so they queue on the mutex instead of polling the
file lock.

`Open` verifies that the journal mode really is WAL and fails otherwise
(a filesystem without shared-memory support cannot host the store).
Write transactions begin with `BEGIN IMMEDIATE`, so a transaction never has
to upgrade a read lock and cannot deadlock against another writer.

Switching a database into WAL mode, which the first open of a new or a
freshly imported store does, takes an exclusive lock for which SQLite does
**not** run the busy handler: of several opens racing on such a store all but
one fail at once with "database is locked". The first connection therefore
retries a busy error with a short backoff, for as long as a writer would
wait. Once the file is in WAL mode the pragma is a no-op and never waits.
(Found by the race-detector run during implementation; pinned by
`TestConcurrentFirstOpens`.)

The API's guarantees carry over, now across processes as well:

- `PutBatch` is one transaction: a reader sees none or all of a batch.
- `All` is one statement, so one snapshot.
- `Delete` reports `ErrNotFound` from the statement's affected-row count, so
  concurrent deletes of one name succeed exactly once.

## Optimistic updates

```go
var ErrConflict = errors.New("refstore: reference is not at the expected key")

func (s *Store) CompareAndSwap(name string, old key.Key, record []byte) error
func (s *Store) Create(name string, record []byte) error
func (s *Store) CompareAndDelete(name string, old key.Key) error
```

- `CompareAndSwap` stores `record` only if the reference currently points at
  `old`: the move from key1 to key2 that happens only while the reference is
  still at key1.
- `Create` stores `record` only if no reference of that name exists.
- `CompareAndDelete` removes the reference only if it points at `old`.

All three return `ErrConflict` when the reference is in a different state
(`Create`: it exists; the others: it points elsewhere) and the two compare
forms return `ErrNotFound` when it does not exist. The caller re-reads and
decides; nothing is retried inside the store.

The comparison is on the **key**, which lives inside the record, so the store
decodes the current record (`reference.Decode`) inside a write transaction:
read, compare, then replace with a statement that is itself guarded by the
bytes just read. A current record that does not decode is an error, never a
match. New records are still stored verbatim and unvalidated, as `Put` does;
`Put`, `PutBatch` and `Delete` stay unconditional.

**CLI.** `ref set NAME KEY --expect OLD` and `ref rm NAME --expect OLD`, where
`OLD` is a key, or `none` for `ref set` meaning the reference must not exist.
A failed expectation exits non-zero and changes nothing; the completeness
walk still runs first, as for an unconditional set.

## Durability

| `sync` argument | Pragmas |
| --- | --- |
| `true` | `synchronous=FULL`, `fullfsync=1`, `checkpoint_fullfsync=1` |
| `false` | `synchronous=NORMAL` |

`fullfsync` matters on macOS only, where a plain `fsync` does not reach the
platter; Go's `File.Sync`, used by the packstore and by Pebble, already issues
the full flush, so this keeps the two halves of a store equally durable.
`NORMAL` never corrupts the database and does not sync on commit, the closest
match to Pebble's `NoSync`.

## Migration from Pebble

Every Pebble directory contains a file named `LOCK`, so one `stat` per open
decides whether there is anything to do. When it exists:

1. Take an exclusive `flock` on `<dir>/migrate.lock`, blocking, so concurrent
   opens migrate once. Re-read the directory afterwards.
2. A `marker.manifest.*` file means a Pebble store is present. If
   `refs.sqlite` does not exist yet, open Pebble read-only (which also takes
   Pebble's own lock, so a store still in use by an old binary fails the
   migration instead of being copied mid-flight), copy every record into
   `refs.sqlite.tmp` with full syncs and a rollback journal, close it, rename
   it to `refs.sqlite` and sync the directory. The rename is the commit point.
3. Write the poison marker `marker.format-version.999999.999`, then move the
   Pebble files into `<dir>/pebble-migrated/`: data files first, the manifest
   markers next, `LOCK` last. A crash anywhere leaves `LOCK` (and, until the
   last step, the manifest marker) in place, so the next open resumes at
   step 2, skips the import because `refs.sqlite` exists, and finishes the
   move. Data written to SQLite after the commit point is never overwritten.
4. No manifest marker but a `LOCK` file is debris: an old binary tried to open
   the migrated store, created its lock file and failed on the poison marker.
   The file is removed.

**Why the poison marker.** An old binary that found no Pebble files would
create an empty Pebble store in `refs/`, report no references, and a
`gc run` from it would reap every object. With the marker, Pebble refuses the
directory ("written in unknown format major version 999").

Only files matching Pebble's naming (`LOCK`, `CURRENT`, `MANIFEST-*`,
`OPTIONS-*`, `marker.*`, `*.log`, `*.sst`, `*.dbtmp`, `temporary.*`) are
moved; anything else in the directory is left alone. `pebble-migrated/` is
kept as a backup and may be deleted by the operator.

## Code layout

| File | Responsibility |
| --- | --- |
| `refstore/refstore.go` | `Store`, `Open`, `Put`, `PutBatch`, `Get`, `Delete`, `All`, `Wipe`, `Close`; unchanged signatures |
| `refstore/cas.go` | `ErrConflict`, `CompareAndSwap`, `Create`, `CompareAndDelete` |
| `refstore/sqlite.go` | file name and format constants, DSN and pragmas, WAL check |
| `refstore/schema.go` | the embedded migrations and the runner described above |
| `refstore/migrations/0001_refs.sql` | the version 1 schema |
| `refstore/queries.sql`, `refstore/sqlc.yaml`, `refstore/generate.go` | sqlc input and the `go:generate` directive |
| `refstore/internal/refsdb/` | sqlc output, committed |
| `refstore/migrate.go` | legacy detection, migration lock, Pebble import, poison marker, moving files aside; the only importer of Pebble |
| `cmd/amber-store/ref.go` | `--expect` on `ref set` and `ref rm` |
| `flake.nix`, `.github/workflows/test.yml` | sqlc in the dev shell; the `sqlc diff` check |

The driver is `modernc.org/sqlite`, a pure-Go build of SQLite, so the module
stays free of cgo. It measured the same as the C library (0.39 ms against
0.32 ms to open, read and close).

## Testing

- The existing tests are the API contract and pass unchanged.
- SQLite behaviour: a nil record reads back empty; two handles on one
  directory see each other's writes and keep batches atomic; a second
  **process** shares the store with a handle that stays open; a directory
  name containing spaces, `?`, `#`, `%` and `&` works; a foreign SQLite file,
  a newer schema version and a non-database file are refused.
- WAL, from inside the package: the journal mode is WAL; the sync flag
  selects the pragmas above; a writer completes while another handle holds a
  read cursor open, and that reader's snapshot does not change; the format
  constants and the version 1 schema text are pinned.
- Migrations: the embedded set is contiguous from 1; a database at version 1
  upgrades through a test-only second migration with several statements and
  keeps its data; a failing migration leaves the version and the data
  untouched; re-opening applies nothing twice.
- Optimistic updates: swap succeeds at the expected key and fails with
  `ErrConflict` at another, leaving the record untouched; absent names give
  `ErrNotFound`; `Create` succeeds once; `CompareAndDelete` mirrors the swap;
  an undecodable current record is an error; of N concurrent swaps from the
  same expected key, across two handles, exactly one wins.
- Pebble migration: records from both an sstable and the write-ahead log
  arrive; Pebble files end up in `pebble-migrated/` with the poison marker in
  place; `pebble.Open` on the migrated directory fails; an interrupted
  cleanup resumes without re-importing over newer data; a stray `LOCK` is
  removed; concurrent opens of a legacy directory all succeed; an empty
  legacy store migrates to an empty database.
- CLI end to end: `ref set --expect` moves a reference, refuses a stale
  expectation without changing it, `--expect none` creates once, and
  `ref rm --expect` refuses then deletes.

## Compatibility

`refstore`'s existing exported API is unchanged; three functions and one
error are added. The on-disk change is one-way: binaries older than this
change cannot open a migrated store, by design. The Go module gains
`modernc.org/sqlite` and keeps `github.com/cockroachdb/pebble/v2` for the
migration only. Developers regenerating queries need sqlc, which the dev
shell provides; building and testing do not.
